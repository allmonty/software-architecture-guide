# P05 — API design: pagination, idempotency and evolution

*A primer on the API decisions that are hard to change later. Rules come from Google's API Improvement Proposals (AIPs) and Stripe's API reference; the trade-off discussion is our reasoning and is labelled.*

## At a glance

Three API decisions cause most long-term pain: how clients **page** through collections, how they **retry safely**, and how the API **evolves** without breaking callers. All three look minor on day one and are close to irreversible once clients depend on them.

**In 60 seconds:** paginate every list from the first version, with opaque cursor tokens; accept a client-generated idempotency key on every create or non-idempotent action and store the first result; and treat the API as a long-lived contract: add, never change, and let clients ignore what they do not recognise.

---

## 1. Pagination `[CONFIRMED]` (Google AIP-158; Stripe API reference)

Google's guidance: collections "can often be arbitrarily sized, and also often grow over time", so "RPCs returning collections of data must provide pagination at the outset, as it is a backwards-incompatible change to add pagination to an existing method." The AIP explains why: a client that listed 75 resources in one call would silently receive only the first page after pagination is added.

- **Opaque page tokens.** Page tokens "must be opaque (but URL-safe) strings, and must not be user-parseable", because if clients can take them apart "they will do so", which turns the implementation into part of the API surface. Base-64 encoding a transparent token is explicitly "not a sufficient obfuscation mechanism".
- **Expiry.** APIs that store tokens in a database may expire them; the AIP gives three days as a rule of thumb.
- **Skipping.** An optional `skip` field counts individual resources, not pages, and if it cannot be fulfilled the response is still 200 with an empty result set.

Stripe's list methods use cursor-based pagination: all list methods accept `limit`, `starting_after` and `ending_before`, which take an existing object ID and return objects in reverse chronological order; the two cursor parameters are mutually exclusive.

**Our trade-off notes `[INDUSTRY PATTERN]`:** offset pagination (`page=3`) is simple but both slow on large offsets and unstable when rows are inserted or deleted during paging; cursor (keyset) pagination is stable and fast but cannot jump to page N. For feeds and logs prefer cursors; for admin tables with small data offsets can be fine. Always cap `limit`.

## 2. Idempotency `[CONFIRMED]` (Google AIP-155; Stripe API reference)

AIP-155: the most important purpose of request IDs is to provide idempotency guarantees, "allowing the same request to be issued more than once without subsequent calls having any effect"; after a network failure the client can retry and "the server can detect duplication and ensure that the request is only processed once."

Stripe's design: for create and update operations the client supplies an **idempotency key**, and "if a connection error occurs, you can safely repeat the request without risk of creating a second object or performing the update twice." Details from the reference (API v1): Stripe saves the status code and body of the first request made with a key, after endpoint execution begins, and retries with the same key return the saved response, including 500 errors; keys are generated by the client (V4 UUIDs suggested), are up to 255 characters, and can be pruned after at least 24 hours; the layer compares incoming parameters with those of the original request and returns an error if they differ, to prevent accidental misuse. If validation fails or a concurrent request conflicts, the result is not saved, because no endpoint execution began. (For its newer v2 API, retries do not repeat successful operations and Stripe retries failed or partially failed work to completion where possible.)

Use of the same ideas elsewhere in the atlas: [17 Payment system](../systems/17-payment-system.md), [10 Notification system](../systems/10-notification-system.md), [01 URL shortener](../systems/01-url-shortener.md), the Photon registry in [31 Ad click aggregation](../systems/31-ad-click-aggregation.md), and consumer-side deduplication in [P03](P03-distributed-transactions.md).

**Our design checklist `[INDUSTRY PATTERN]`:** make the key part of the request, scope it to the caller, store key + request fingerprint + response atomically with the side effect, define what happens to concurrent duplicates (wait or reject), define retention, and say which operations are naturally idempotent (PUT and DELETE semantics) so you do not need keys.

## 3. Evolution and versioning `[CONFIRMED]` (Stripe API reference; Google AIP-158)

Stripe's process: starting with the 2024-09-30.acacia release it ships new API versions monthly "with no breaking changes", and twice a year a new major release that starts with an API version containing breaking changes; clients choose a version with a request header and use the account default otherwise; webhook events use the account's default version. Enums can be **closed** (fixed) or **open**: "Stripe can add new values as a backward-compatible change without requiring an API version upgrade", and clients are told not to assume documented values are exhaustive and to include a safe fallback branch.

The AIP-158 example above shows the other rule: some changes that look additive (adding pagination) are behaviourally breaking.

**Our rules of thumb `[INDUSTRY PATTERN]`:** adding an optional field or a new endpoint is safe; removing or renaming a field, changing a type, changing defaults, or adding a required parameter is breaking; clients must ignore unknown fields; pin a version per client; give deprecations a long, announced runway with usage metrics.
