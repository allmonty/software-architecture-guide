# C01 — Amazon S3 outage, US-EAST-1, February 2017

*A real incident, told from the operator's own published account. The lessons section is our analysis and is labelled as such. Sources and what was not checked are at the end.*

## At a glance

**What happened.** An operator ran an approved playbook command to remove a few servers from a billing subsystem. One input was wrong, a much larger set of servers was removed, and two core S3 subsystems had to be fully restarted. S3 in US-EAST-1 could not serve requests while those subsystems restarted (partial service from 12:26 PM, normal operation at 1:54 PM), and other AWS services that depend on S3 failed with it.

**Key facts** (as published)
- Start: 9:37 AM PST on 28 February 2017; the index subsystem began serving GET, LIST and DELETE at 12:26 PM and was fully recovered at 1:18 PM, and the placement subsystem finished at 1:54 PM `[CONFIRMED]`.
- The command removed servers that supported the **index** subsystem (metadata and location of all objects) and the **placement** subsystem (allocation for new objects) `[CONFIRMED]`.
- The status dashboard could not be updated until 11:37 AM because its console depended on S3 `[CONFIRMED]`.

**Why it matters for architects.** (Our reading.) A routine, trusted operation whose tool allowed too much capacity to be removed too quickly, a recovery path that had not been exercised at current scale, and a monitoring surface that depended on the failing service.

---

## What happened `[CONFIRMED]`

At 9:37 AM PST an authorized S3 team member, while debugging a billing slowdown and using an established playbook, ran a command meant to remove a small number of servers. As AWS puts it, "one of the inputs to the command was entered incorrectly and a larger set of servers was removed than intended." The removed servers supported the index subsystem, which handles GET, LIST, PUT and DELETE metadata, and the placement subsystem, which allocates storage for new objects and needs the index subsystem to work. Removing a significant portion of capacity forced both to restart fully. While they restarted, S3 could not serve requests, and services that rely on S3 in the region (the S3 console, new EC2 instance launches, EBS volumes needing snapshot data, and Lambda) were affected. By 12:26 PM the index subsystem had enough capacity to begin serving GET, LIST and DELETE, and by 1:18 PM it was fully recovered; PUT needed the placement subsystem, which finished at 1:54 PM. Some dependent services then needed extra time to work through backlogs.

## Contributing factors `[CONFIRMED]`

- The tool let too much capacity be removed too quickly.
- The index and placement subsystems had not been fully restarted in larger regions for many years; S3 had grown a great deal, and restarting plus the safety checks that validate metadata took longer than expected.
- The Service Health Dashboard administration console depended on S3, so AWS used Twitter and banner text until 11:37 AM.

## What the company changed `[CONFIRMED]`

- The tool now removes capacity more slowly and refuses to remove capacity if a subsystem would drop below its minimum required level; other operational tools are being audited for similar checks.
- Work to speed the recovery of key S3 subsystems, including further partitioning into small units AWS calls cells.
- The dashboard administration console now runs across multiple regions.

## 🔧 Our analysis (not from the source)

**Questions a design review could have asked**
- What is the largest blast radius any single operator command can have, and where is that limit enforced: in the tool, or only in the operator's care?
- When did we last restart each stateful core component from cold at today's size, and how long does the validation step take?
- What do our status page, runbooks, paging and deployment tools depend on, and do they work when the main service is down?
- Which dependent services degrade gracefully when this service is unavailable, and which fail hard?
